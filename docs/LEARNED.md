# LEARNED.md — Append-Only Lessons Log

Lessons from owner corrections and self-caught mistakes, appended by AI agents
per the Debugging Protocols section of CLAUDE.md. Never rewrite or delete an
existing entry — refine a similar lesson in place instead of duplicating it.
On conflict with CLAUDE.md, this file wins.

Entry format:
`- YYYY-MM-DD [status]: <rule> (trigger: <what went wrong>)`

One lesson per entry. An entry may run to a paragraph — several of the most
useful ones do. Do not compress a lesson to fit a line.

The status tag says whether a lesson is still carried in prose or has been made
mechanical. Promoting an entry is the point; the `new-audit` skill exists for it.

- `[audit]`    enforced by a script in tests/, run by `npm test`
- `[hook]`     enforced by a hook in .claude/hooks/
- `[skill]`    encoded as a step in a skill under .claude/skills/
- `[advisory]` carried in prose only — still live risk

- 2026-07-12 [audit]: When adding behavior to a system-level entry point, grep for sibling paths that bypass it before claiming coverage — ps.setNormalized resolved tables but nearly every controller called p.setNormalized directly, so tables silently never applied to MIDI/mouse/sound (trigger: owner asked "do tables auto-scale?"; the honest answer was "they mostly don't run").
- 2026-07-12 [skill]: An occluded/backgrounded Chrome tab freezes rAF entirely — render loop AND controller ticks stop; automated sweep tests read as failures while the code is fine. Check the app's FPS readout (0 fps = invalid test) before debugging the code (trigger: two "broken" recall-range test runs were just a hidden window).
- 2026-07-30 [audit]: "Append-only" protects a list's own indices, not indices in a list built by appending something AFTER it — before appending to SOURCE_DEFS, check every derived array with a tail (CAPTURE_SOURCES pins FG/BG/DS Src at SOURCES.length, so source 29 would have rotated them to 30/31/32 in five saved capture params). Stamp the base in the file and migrate on load; a frozen high base puts holes in dropdowns and controller travel (trigger: Blueprint §6 instructed "append at index 29" and nothing in the append-only rule flagged the collision).
- 2026-07-30 [audit]: An exponential approach (slew, smoothing, easing) stored in a HALF-FLOAT buffer freezes short of its target — near 1.0 one ulp is ~1e-3, so once the per-frame step falls below that it rounds to no change and never arrives. Replace any step smaller than an ulp with exactly one ulp in the right direction, clamped against overshoot. And sample convergence at TWO horizons: a stall is indistinguishable from convergence if you only look once (trigger: rutt slew sat at 98.51 vs 100.91, bit-identical at frame 300 and frame 2000; the first guess was resampling through the history buffer, disproved by measuring the resampled-no-lag reference at 100.906). REFINED 2026-08-05 — the rule is not about half-float, it is about ANY exponential accumulator whose per-frame step can fall below one representable level, and the fix is not always a progress floor: sometimes it is simply the right buffer. Motion Extraction repeated this in an 8-BIT background, which is 8x coarser than half: `mix(bg, cur, adapt)` at `Bg adapt` 4s gives a step of 2.9e-3 against an 8-bit level of 3.9e-3, so the background froze on the frame it was primed with and NEVER moved again — above ~2.95s nothing could move it for any difference at all, including full black-to-white. It did not look like a precision bug: it looked like a beautiful static reference plate, and produced clean silhouettes, so it read as the feature working until the owner noticed it was always the first frame. Float32 was chosen over a progress floor because a floor relinearises the tail and would have made the long end of a 0–10s range a lie; measured 8-bit closed 2% of a gap in 10s where float32 closed the specified 82%. **Before storing an exponential in any buffer, divide the smallest per-frame step by the buffer's resolution and check the quotient is comfortably above 1.**
- 2026-07-30 [audit]: A new source must be wired into BOTH resolvers — `Pipeline._resolveSource()` (layers and mix buses; falls through to `inputs.color`) and main.js `_resolveLayerTex()` (engine-internal selectors like sdf.texSrc / td.mapSource / rutt.source; falls through to Output). Wiring only the second passes an audit that only checks the second, while routing the source to FG paints a solid frame in whatever hue the Color generator happens to be (trigger: Rutt-Etra rendered a flat RED screen on FG; audit reported a clean 30/30 because it parsed only _resolveLayerTex — it now checks both, and was confirmed to fail without the fix).

- 2026-07-30 [audit]: Any geometry expanded AFTER projection (screen-space ribbons, billboards, thickness quads) has a winding that depends on where the camera is — set `side: THREE.DoubleSide` or it culls itself at some angles and not others. Reads as "the source is broken", not "the winding is backwards", when the dead angle happens to be the default (trigger: Rutt-Etra rendered nothing at rutt.angle 0 — its default — and fine at 65°; lit-pixel count was 0 with a forced-white fragment, which is what ruled out luminance and pointed at culling).
- 2026-07-30 [skill]: Assert the RELATIONSHIP a control should have, with a direction, and pick a metric the control can actually move — then check the margin is not marginal. Three ways this went wrong in one feature: (a) beam width measured at 60 lines gave 1.16× across a 6× change because the lattice already filled the frame (saturated — at 8 lines it is linear to within 0.5%); (b) a gamma tested on lit-AREA gave a 43-pixel margin against a threshold of 40, which a dead knob would nearly pass; (c) the same gamma tested on vertical EXTENT gave 107 vs 107 on working code, because pow(0,g)=0 and pow(1,g)=1 leave a full-range ramp's endpoints invariant by construction — only the centroid moves; (d) a red-left/blue-right source has mean R == mean B by symmetry, so channel MEANS score a grey render and a fully chromatic one identically — measure per-pixel |R−G|+|G−B|+|R−B| instead (trigger: four wrong metrics across three knobs; two failed on correct code, one nearly passed on nothing, and one PASSED FOR THE WRONG REASON).
- 2026-07-31 [skill]: The one-canonical-source-list rule has a second failure mode nobody was watching: a param with its OWN short option menu, mapped to SOURCE_DEFS by a literal array of bare NUMBERS. `_sdfSrcToLayerIdx` was written against an older ordering and drifted three ways at once — "Draw"→3D Scene, "3D"→Noise, "Noise"→Color2, a solid cyan fill. - 2026-07-31 [skill]: Two verification traps in one session, both of which produce numbers that look fine. (a) A service worker (`imweb-v0.7`) serves a CACHED index.html on localhost, so `curl` returns the new markup while the tab renders the old — every new container id read as MISSING. Unregister the SW and clear caches before concluding a DOM change did not land. (b) `drawImage(webglCanvas)` into a 2D canvas returns a STALE frame without `preserveDrawingBuffer` — four different source selections gave bit-identical luma/chroma to 0.1 while the field was visibly animating. - 2026-07-31 [audit]: When a rename also changes UNITS, the property to test is not "did the keys change" but "does the thing still land in the same place" — assert the round trip against the consumer's own formula, then run it over the real saved file, not just fixtures. sdf.camX/Y/Z → orbit/elev/distance passed 45 of 45 camera maps in MasterProject.imweb at exactly 0 error, which is the only evidence that a migrated project opens looking identical. And carry only the settings that still mean the same thing — recall bounds in world units are meaningless on a 0–360° axis, so reset them rather than importing a ±1.4 sweep onto a parameter that runs to 360 (trigger: sdf camera rework; the owner's project had ctrlMin/ctrlMax and a response table on camX/camY).
- 2026-07-31 [audit]: Defaults chosen to REPRODUCE the constant they replace are what make "expose this hardcoded value as a param" a safe change — decompose the literal instead of picking a round number. vec3(0.5,0.1,0.8) is HSV(274°, 0.875, 0.8); normalize(vec3(1,1.5,2)) is az 27° / el 34°; uv*0.75 is a 73.74° vertical FOV. Each default was derived, so no existing render moved (trigger: four hardcoded values exposed at once in the SDF shader).
- 2026-07-31 [skill]: A new entry in an existing menu inherits an unwritten spec from its neighbours — MEASURE the family before adding to it. Five shapes appended to sdf.shape shipped at bounding radii 0.64/0.71/0.75/2.06/unbounded against a family that sits between 0.50 and 0.73, and the owner's first words on seeing them were "much larger than the older ones". Worse, two were wrong in KIND, not degree: a gyroid is triply-periodic and has no size of its own, so it ignored Size, Separation and Count and read as a background rather than a shape; a catenoid's flare is exponential, so its y clamp IS its size control (cosh(0.7/0.25) = a mouth 3.4x the family). Compute the bounding radius of every existing option and the new one before wiring the menu (trigger: shapes borrowed from Rutt-Etra's parametric list, sized from the source formulas instead of from the family they were joining).
- 2026-07-31 [skill]: Never `await` a bare requestAnimationFrame from an automation probe — a backgrounded tab suspends rAF, the promise never settles, and the CDP call dies at its 45s timeout looking exactly like a frozen renderer. Two "renderer wedges" in one session were this, and the second one nearly got blamed on a giant unrolled shader. Race every rAF against a setTimeout, and check `document.hidden` FIRST: hidden means the render loop is stopped, so 0 fps, stale param readouts and a black canvas are all expected and every in-app observation is void (extends the hidden-tab entry above with the failure MODE, not just the symptom). REFINED 2026-08-05 — "stale param readouts" is sharper than it sounds and cuts the other way too: PARAM ROW DISPLAYS are refreshed from the render loop, but onChange listeners fire synchronously, so after a programmatic param change a hidden tab shows the flow diagram already updated while the row still reads the OLD number. That looks exactly like a partial failure — "the reset fired but the panel did not update" — and it is tempting to go fix a UI bug that does not exist. A `Clear All FX` trigger was on the point of being diagnosed that way; one screenshot to force a frame showed every row correct. The rule: when two views of the same value disagree in a hidden tab, force a frame BEFORE forming any hypothesis — the one driven by listeners is live, the one driven by the loop is a photograph of whenever the last frame ran.
- 2026-07-31 [advisory]: Before taking over a channel that currently holds a constant, find out what the CONSUMER wants from it. Packing SDF depth into alpha looked free — alpha was a constant 1.0 and nothing read it — but it (a) silently enabled NormalBlending's src.a multiply, dimming every hit by its own depth and multiplying every MISS by zero, which deleted the background aura, and (b) spent the one channel the compositor needs to know where the source IS, closing the keyer's Alpha mode, which was the correct fix for the owner's actual complaint. "Unused" meant "not yet used", not "free". A full-screen write into a source target wants the shader's RGBA verbatim: set `blending: THREE.NoBlending`. REFINED 2026-08-02 — three.js only applies blending when the material opts in: `(blending === NormalBlending && transparent === false) ? NoBlending : blending` (three.cjs, verified in node_modules). So a plain opaque ShaderMaterial is already safe, and the dangerous combination is specifically `transparent: true` (or any non-Normal mode) together with non-constant alpha. That is why this resisted promotion to an audit: the natural file-level rule flags ParticleRender and ParticleSystem, where `transparent: true` belongs to the Points material that is SUPPOSED to blend additively, not to the full-screen quad — 2 false positives out of 16. Stays [advisory] until per-material association is worth the parser (trigger: owner reported a dull glow, then a black halo; both were this, two turns apart).
- 2026-07-31 [advisory]: Do not let one variable control both WHERE a gradient is and HOW BRIGHT it is — the falloff will extinguish the far stop and that stop becomes unreachable at any setting. Aura brightness used halo^2 while the colour mix used halo, so by 76% of the way to Hue 2 luma was 0.010: the second colour of a two-colour gradient could be set to anything and never appeared. Same shape of bug as a multiply-by-environment that can reach zero (Glow Env took the aura to luma 0.004 over dark surround) — normalise to take the hue and leave the level alone. And a matte composite `mix(bg,fg,a)` is BACKWARDS for anything emissive: a glow adds light rather than occluding, so the background shows through it as shadows; use `bg*(1-a)+fg` (trigger: three wrong diagnoses of "no outer glow" before reconstructing the fragment path numerically against the owner's real slider values).

- 2026-07-31 [skill]: `.imw-sel-trigger` TOGGLES its menu, so a probe that opens a menu and then fails leaves it open — and the next attempt CLOSES it, reporting "menus=0" forever. - 2026-08-04 [advisory]: A metric that is CAPPED cannot answer a question about cost. Four soak phases on a real iPad returned avg_ms 16.675 / 16.670 / 16.670 / 16.670 for deck-B-empty, loaded-idle, both-live and recovered — all four pinned at the 16.67ms vsync ceiling, because the device was never saturated. "The idle-deck gate fires" and "the deck uploads and there is headroom to absorb it" are INDISTINGUISHABLE in frame time by construction, so the phase-2-vs-phase-1 comparison the protocol is built around could only ever produce a PASS that means nothing. Extends the 2026-07-30 saturation lesson (beam width at 60 lines) from "pick a metric the control can move" to "check the metric is not already at its limit before the run, not after". The fix was not a longer soak but a different observable: three integer counters in MovieInput.uploadIfNewFrame (ticks/gated/uploads) settled it in 65 seconds — deckB gated 3917 with uploads frozen at xfade 0, then uploads +46616 with gated 0 at xfade 0.5. Count the EVENT you care about; do not infer it from an aggregate that something else is clamping (trigger: 55 minutes of measured phases that answered the thermal question and could not, even in principle, answer the gating one).
- 2026-08-04 [advisory]: A console readback that does not clear on navigation will show you a log you just DELETED. After removing the render-loop `DC:` log and rebuilding, `read_console_messages` still returned 200 `DC: 4 Tri: 8` lines across two fresh navigations — the buffer accumulates across page loads, so the entries were history, not live output. The near-miss conclusion was "the service worker is serving a stale bundle", which is a real hazard here and would have sent the fix in a circle. Settle it with evidence the old build CANNOT produce, not by re-reading the same channel: the loaded bundle's content hash matched the build output exactly, and `__dbg.state()` carried a `draws` field that only exists in the new code. Same family as the drawImage stale-readback and the hidden-tab rAF entries — when a readback and a source disagree, suspect the readback (trigger: three tool calls spent proving a removed log was removed).
- 2026-08-04 [audit]: **"three still exports the constant" is not "three still supports the upload."** `THREE.RGBFormat` still resolves in r168 — it is in the constant table, `WebGLUtils.convert` maps it to `gl.RGB`, and nothing is undefined or warns — but `getInternalFormat` picks no SIZED internal format for RGB (it upgrades RED/RG/RGBA and only touches RGB for `UNSIGNED_INT_5_9_9_9_REV`). So `RGBFormat + FloatType` went out as unsized RGB + FLOAT, which WebGL2 rejects: `texImage2D` raised INVALID_OPERATION, the texture stayed incomplete, and every `texture2D()` against it returned (0,0,0,1). Load a .cube, raise LUT Amount, whole picture black — the colour grade panel had never worked in WebGL2. Verifying that a name resolves proves nothing; the constant table and `getInternalFormat` disagree and only the second one runs, so read the conversion path in `node_modules/three` rather than checking the export exists. The second half is the same bug one device away: a linearly filtered **RGBA32F** needs `OES_texture_float_linear` and samples black without it, while **RGBA16F** is filterable in core WebGL2 — so half-float is the correct storage for anything sampled with LinearFilter, and the desk would never have shown the difference. Nothing downstream can catch either one, because solid black is a picture this instrument is allowed to produce (trigger: owner reported "loading a .cube and adding LUT amount turns the image to black"; the first hypothesis — that r152 removed the constant — was wrong in its reason and right in its fix, and the real mechanism only came out of reading getInternalFormat and then reproducing INVALID_OPERATION against a real WebGL2 context).
- 2026-08-04 [skill]: A colour-transform fixture must be chosen so that the transform CANNOT be confused with the input — the obvious choices all hide it. Verifying the LUT fix in-app, an R↔B swap was invisible because the default Noise source is greyscale (r==g==b, so the swap is the identity), and an invert of greyscale noise still looks like greyscale noise. Neither read as a failed test; both read as "the LUT is not doing anything", which is exactly the bug's own symptom. A **constant-colour `.cube`** (every one of the N³ entries magenta) settles it in one screenshot: the whole canvas must become that colour regardless of input, so "applied" and "not applied" cannot be mistaken for each other, and sweeping the amount 0 → 50 → 100 then proves the blend rather than just the endpoint. For the numeric half, do not test through the app at all — drive the exact shader over known input colours in a raw WebGL2 context and read pixels back (six colours, maxErr 0/255), with `gl.getError()` after the upload as the direct evidence. Same family as the drawImage and console-buffer entries: when the readback cannot distinguish pass from fail, change the fixture, not the reasoning (trigger: two fixtures in a row produced screenshots that looked identical whether or not the fix was present).
- 2026-08-04 [advisory]: Preconditions verified BY EYE are not verified. Three separate soak runs were invalidated by the same class of error — `layer.bg` pointing at Movie B, `layer.ds` pointing at Camera (dead over http on iOS, so displacement was invisible at any amount), `displace.amount` and `keyer` both still 0 while the chain was believed to include them, `mix.xfade` at 0.427 when the phase required 0 — and every one was confirmed "set correctly" by a human looking at sliders before the run. ParameterSystem is module-scoped, so nothing could read the patch back. Worse, `layer.fg`/`bg`/`ds` all feed `_direct()`, so ANY of them pointing at the source under test silently forces its upload flag true and makes the gate untestable, which reads as "gating is broken" rather than "the patch cannot test gating". Two fixes, both cheap: a debug handle returning every precondition in ONE call, and carrying the phase-defining values on EVERY telemetry row so a run proves its own conditions instead of depending on memory — that is what caught a phase marked before the crossfade was zeroed, and let the bad prefix be cut cleanly rather than silently averaged in (trigger: five false starts across one session; see src/soak.js).
- 2026-08-02 [audit]: Promoting a prose lesson to an audit finds the cases the lesson never covered — write the test against the RULE, not against the incident. The 2026-07-10 bank-save lesson named one file (Bank 1.imweb) and one extension; the audit written from it checked all three of .imweb/.imstate/.imbank against hypothetical future names and failed on its first run, because `.imstate` had no re-ignore at all — `!public/**` left every exported Display State one `git add .` from shipping to a public repo. `.imbank` had been patched the same way months earlier, with a comment explaining the hazard, and `.imstate` was still missed both times. A lesson protects the case that burned you; an audit protects the case that hasn't yet (trigger: first run of tests/audit-gitignore-banks.mjs, promoting the oldest advisory entry).
- 2026-08-05 [audit]: **A UI table keyed by id is a second registry, and a new entry is invisible until it is in BOTH.** Adding nine effects to `DEFAULT_FX_ORDER` wired them into the render chain completely — they ran, they were automatable, they saved and recalled — and left them absent from the signal-flow display, which is also the drag-to-reorder UI. So a new effect could be used but never SEEN or MOVED, and the symptom ("the flow display is missing something") points at the display rather than at the missing `_FX_NODE_INFO` row. Exactly the shape the panel-coverage audit already guarded for params, one table over: `pick()` lists cover `effect.*` params, and nothing covered fx ids. Promoted immediately into the same audit and confirmed to fail with an entry removed. The general rule: when a feature has a registry and a presentation table keyed by the same id, an audit must assert the two agree — a rule about ONE of them is half a rule (trigger: nine effects added in one commit; caught while wiring the ninth, not by anything mechanical).
- 2026-08-05 [audit]: **A list persisted for ORDER is also a filter, and a filter silently deletes what it does not recognise.** `pipeline.setFxOrder` filtered a saved order to known ids, which is correct for stale ids and catastrophic for NEW ones: the chain order is captured by Display States and written into every `.imweb` file, so the moment an effect ships, every state on disk recalls with that effect missing from the chain. Row present, slider moves, readout updates, nothing renders — and the natural conclusion is that the new effect is broken, not that a five-year-old state is filtering it out. Unknown-but-current ids must be APPENDED at their default position rather than dropped. Same family as the capture-base entry (2026-07-30): appending to a list is safe, but anything that persists a SUBSET of that list needs a merge on load, not a filter (trigger: found while adding effects, before shipping — every effect in this release would have failed to appear for any saved state).
- 2026-08-05 [skill]: **`vite preview` builds its file map at STARTUP, so a rebuild is not served until the server is restarted** — and the symptom is indistinguishable from the service-worker cache trap above it. Three unregister/clear/force-reload cycles all kept loading the old bundle hash while `fetch('/index.html', {cache:'no-store'})` returned the NEW one; the SW was innocent. Settle which layer is stale by comparing `document.scripts[0].src` against a no-store fetch of index.html: if they disagree the PAGE is stale (SW/browser cache), if they agree and both are old the SERVER is stale (restart it). Restart preview after every build as a matter of course. Related: ImWeb registers `beforeunload` via `addEventListener`, so `window.onbeforeunload = null` cannot remove it and scripted navigation in the owner's tab is cancelled by the Leave-site dialog — verify in the Browser pane instead, which takes `force: true`, has its own localStorage (the owner's live patch is never touched) and starts from defaults; note its camera is blocked, so use FG = SDF over a Noise BG as the fixture (trigger: ~10 tool calls spent proving a service worker was not the problem).
- 2026-08-05 [audit]: **A hazard that only exists ACROSS passes cannot be caught by a guard that compares values within one.** The feedback transforms ping-ponged through the same two render targets that held the composited live frame, so whether the second transform overwrote it depended on how many passes the keyer/chroma/warp chain had run earlier that frame — parity, not intent. When it landed wrong the blend received the transformed prev frame as BOTH inputs and the live picture vanished, which reads as an artistic property of feedback rather than as a buffer bug, and comes and goes as unrelated effects are toggled. `_pass()`'s identity guard is structurally unable to see it: nothing is aliased at the moment of the write; the clobbered texture is read LATER. CLAUDE.md's "identity checks beat flags" is the right rule for aliasing and says nothing about lifetime — the fix for lifetime is a dedicated target (as the mix buses already do), and the invariant belongs in a static audit because a still frame cannot show it. Suspect this for any effect that holds a texture across more than one pass (trigger: the first FBDecay test rendered a near-black frame with the live picture gone; the cause was diagnosed from the ping-pong parity, not from the symptom).
- 2026-08-07 [advisory]: **A rejected promise inside `respondWith()` reaches the page as a bare "Failed to fetch" — a service worker can manufacture a network error out of a storage hiccup.** The owner reported the Help menu's Full Manual failing with `Failed to fetch`, which is a TypeError with no status behind it and is indistinguishable from the server being down; `curl` returned 200 on both ports and it could not be reproduced in the Browser pane on either. The mechanism was in `public/sw.js`: `caches.match()` and `caches.open()` were both unguarded, and either can reject (storage disabled, quota, private mode, a devtools "clear site data" landing mid-request) — a rejection there rejects the promise handed to `respondWith`, and the page's own `fetch()` throws. **Wrap every path inside `respondWith`, including the cache lookups; a service worker must never be able to fail louder than the network it is standing in front of.** Two more bugs surfaced in the same eleven lines: the handler was cache-first for EVERYTHING, so `/docs/*.md` served whatever revision a reader opened once and an edited manual could never reach them (docs are now network-first with cache fallback — the offline case cache-first was actually for); and `APP_SHELL` lists dev-only paths (`/src/main.js`, `/src/style.css`) while `addAll()` is all-or-nothing, so on any built site one 404 rejected the install and the worker never activated. `vite preview` hides that last one by serving index.html as the SPA fallback for unknown paths, so the 404s come back 200 and the install "works" on exactly the surface you would test it on. Cache the shell entry-by-entry with a per-entry catch (trigger: a bug report that could not be reproduced, whose three real causes were all found by reading the fetch handler rather than by chasing the symptom).
- 2026-08-06 [audit]: **A scale change with an unchanged KEY is the one migration the data cannot describe, so it needs a stamp — and the stamp is the part that rots.** Moving layer.fg/bg.blendAmount from 0–1 to 0–100 % left the ids alone, which removes the property every other migration here leans on: migrateSdfTile and migrateSdfCamera know they have run because the old key is gone, but 0.5 is legal in both blend schemes (half, and half a percent) and no amount of inspection separates them. The tempting shortcut — "values ≤ 1 must be legacy" — is wrong in a way that only shows up later, silently multiplying a deliberate 0.5 % by 100 on every load. So the rule: **if a migration cannot be expressed as "the old key is present", it needs a version stamp on every write path, and the audit must check the WRITE paths, not just the conversion.** The conversion is the easy half and passes trivially; the failure that actually ships is one of the four formats (.imweb / .imbank / .imstate / IndexedDB) forgetting to stamp, after which that format alone halves its blend on the next load — small enough to read as a rendering difference rather than a data bug. - 2026-08-08 [audit]: `step` on a Parameter is the UI drag increment, not a value quantum — controller-driven writes must bypass sub-unit snapping, or slow modulation stutters while the fps counter reads 60. A `step: 0.01` param over a 0–1 range has only 100 places to land, so a sine LFO moved the value on 560/600 frames at 1 Hz but 30/600 at 0.01 Hz and 4/600 at 0.001 Hz. Nothing errors and the renderer is genuinely fine, which is why this reads as a mysterious perf bug and why the fps counter is the wrong instrument to reach for: when motion looks wrong but fps is healthy, measure how often the PARAMETER changes, not how often the frame does. Integer steps are the opposite case and must keep snapping — octaves, sdf.count and rutt.lines are the value, not a display rounding. (trigger: owner reported 0.01 Hz LFOs stuttering at a reported 60 fps.)
- 2026-08-08 [audit]: A slew that must ease IN needs VELOCITY state carried across frames, not a fixed-duration interpolation. The one-pole lag cannot ease in by construction — its speed is greatest on the very first frame after the target moves, which is exactly the hard direction change an S+H complains about. The obvious repair, a timed smoothstep segment restarted whenever the target changes, passes a single-jump test and then freezes solid on a continuously moving source, because a sine changes its target every frame and restarts the segment every frame. A critically damped spring has neither failure. Also: a response table is NOT a slew curve — tables reshape which value comes out, slew reshapes how it travels in time, so reaching for an S-curve table to soften an S+H changes the wrong axis. (trigger: owner asked for elegant ease-in/ease-out on S+H and noted tables were not helping.)
- 2026-08-08 [audit]: A slew curve is either a FILTER or a SEGMENT, and the two cannot be unified — say which before writing one. A filter (one-pole lag, critically damped spring) has no clock and no endpoint, so it chases a live target and behaves the same on stepped and sweeping sources; it can never overshoot, ring or bounce, because those need to know how far through the move you are. A segment curve f(k), k∈[0,1], can do all of that, but it needs a captured start, an endpoint and a clock — and the naive arming rule (restart the clock whenever the target changes) pins k at 0 forever on a sine, which retargets every frame. The rule that works: arm a new segment only when the previous one has LANDED (`_slewK >= 1`), and re-aim at the live target during flight without touching the clock. Even then a segment curve barely smooths a sweeping source and adds ~25–50x the frame-to-frame jerk of a filter, so group them in the UI by which family they belong to rather than presenting seven interchangeable flavours. (trigger: owner asked to add Super Ease, Exponential, Elastic, Bounce and Back beside the existing Lag and Ease.)
